# Интеграция фронтенда с бэкендом Kudaibergen

Этот документ — для команды, которая пишет клиент (мобильное приложение или веб) поверх
этого API. Он описывает не «что есть в коде», а то, как клиенту правильно им пользоваться:
последовательность запросов, форматы, коды ошибок, WebSocket и по каким правилам сейчас
живёт «сделка» между покупателем и магазином.

Актуально на дату последнего изменения этого файла. Если сомневаешься — сверяйся со
Swagger UI (`/swagger-ui.html`) или `/v3/api-docs`, он генерируется из кода и не может
разойтись с реальным поведением.

## Базовые вещи

- Base URL (dev): `http://localhost:8080`. Все бизнес-эндпоинты — под `/api/v1/...`.
- Формат — JSON, `Content-Type: application/json`, кодировка UTF-8.
- Пагинация везде одинаковая — `page` (с 0), `size` (обычно `max 100`), ответ:
  ```json
  { "content": [...], "page": 0, "size": 20, "totalElements": 42, "totalPages": 3 }
  ```
- Формат ошибки — всегда один и тот же, даже для 500-х:
  ```json
  { "code": "REQUEST_EXPIRED", "message": "Срок ответа на запрос истёк", "field": null }
  ```
  `field` заполняется только для ошибок валидации (`VALIDATION_ERROR`) — туда падает имя
  невалидного поля. `code` — это то, на что должен ветвиться клиент (не парсить `message`,
  он на русском и для показа пользователю как есть).

  Частые коды: `VALIDATION_ERROR` (400), `BAD_REQUEST` (400), `UNAUTHORIZED` (401),
  `FORBIDDEN` (403), `NOT_FOUND`/`*_NOT_FOUND` (404), `CONFLICT`/`*_ALREADY_EXISTS` (409),
  `INTERNAL_ERROR` (500).

- **Idempotency-Key**: на создающих эндпоинтах, где обрыв связи мог бы привести к дублю
  (`POST /requests`, `POST /offers`, `POST /offers/bulk`), можно (не обязательно) передать
  заголовок `Idempotency-Key: <uuid>`. Повторный запрос с тем же ключом вернёт тот же
  сохранённый ответ, ничего заново не создаст. Генерировать ключ клиенту нужно один раз на
  попытку действия (не на каждый retry заново).

## Авторизация

Вход только по номеру телефона + SMS-код, без пароля.

1. `POST /api/v1/auth/request-code` `{ "phone": "+996700123456" }` → `{ expiresInSeconds,
   debugCode }`. `debugCode` приходит только в dev (`SMS_EXPOSE_CODE=true` на бэкенде) —
   в проде поле будет `null`, код придёт по SMS. Не чаще раза в минуту на номер.
2. `POST /api/v1/auth/verify` `{ phone, code }` → `{ accessToken, refreshToken,
   expiresInSeconds, isNewUser, role }`.
   - Если `isNewUser: true` — у пользователя ещё нет роли, следующим шагом обязателен
     `register-role`, иначе большинство эндпоинтов ответят 401/403.
   - `role` при первом входе будет `null`/отсутствовать до регистрации роли.
3. Если `isNewUser`: `POST /api/v1/auth/register-role` (с `Authorization: Bearer
   <accessToken>`) `{ role: "BUYER" | "SELLER", name, storeName?, businessType?, city? }`
   → новая пара токенов с проставленной ролью. Для `SELLER` магазин создаётся
   автоматически по `storeName`/`businessType`.
4. Все остальные запросы — заголовок `Authorization: Bearer <accessToken>`.
5. `accessToken` живёт 15 минут (`expiresInSeconds` в ответе), `refreshToken` — 30 дней.
   По истечении access-токена: `POST /api/v1/auth/refresh` `{ refreshToken }` → новая пара.
   Обычная схема — обновлять access по 401 или превентивно за минуту до истечения.

Роли: `BUYER`, `SELLER`. Весь `/api/v1/my-store/**` (кабинет продавца) требует роль
`SELLER` — покупателю туда 403.

## Основной флоу продукта

Это то, что реально нужно понимать, чтобы собрать экраны правильно — а не просто список
эндпоинтов.

1. **Покупатель создаёт запрос** — `POST /api/v1/requests` (веерная рассылка: бэкенд сам
   находит магазины по категории и уведомляет их, `sellersMatched` в ответе — сколько
   магазинов затронуто). Город больше не фильтрует подбор — только категория.
2. **Продавец видит запрос в ленте** — `GET /api/v1/my-store/requests?filter=UNANSWERED|URGENT|ALL`.
3. **Продавец отвечает** — либо на один запрос (`POST /api/v1/offers`), либо массово шаблоном
   сразу на несколько (`POST /api/v1/offers/bulk`, «быстрый ответ всем продавцам», это
   основная фича продавца — используйте её как основной путь ответа в UI, а не поштучный
   `POST /api/v1/offers`).
4. **Оффер сразу прилетает покупателю сообщением в чат — не отдельным экраном на ожидании.**
   Ответ продавца автоматически создаёт (или переиспользует) чат между покупателем и этим
   магазином и шлёт туда текстовое сообщение с ценой/сроком доставки/комментарием —
   покупателю не нужно заходить в список предложений и ждать: чат с офером уже есть в
   `GET /api/v1/chats` сразу после ответа продавца, доставляется как любое обычное
   сообщение (WS, живой инбокс, пуш с учётом «уже смотрит этот чат»). Структурные данные
   оффера (цена, статус, для сравнения/сортировки) по-прежнему доступны в
   `GET /api/v1/requests/{id}` (поле `offers`), но это уже не основной путь для покупателя.
5. **Открытие чата = сделка.** Чат с магазином (независимо от того, что его создало — оффер
   или прямое «написать» с карточки магазина) даёт:
   - в `GET /api/v1/stores/{id}` магазину открывается номер телефона филиалов (`phone` в
     `branches[]` до этого — `null`);
   - покупателю становится доступен `POST /api/v1/stores/{id}/reviews` (иначе — 403);
   - это же засчитывается в аналитику продавца как закрытая сделка (`dealsClosed`).
6. **У покупателя с каждым магазином — один чат**, а не один на запрос. Если у покупателя уже
   есть переписка с магазином (с прошлого запроса или просто «написали напрямую»), новый
   оффер от этого же магазина на новый запрос допишется в ту же самую переписку, не откроет
   параллельный тред. `POST /stores/{id}/chat` тоже всегда возвращает этот единственный чат.

## Профиль и автомобили

- `GET /api/v1/me`, `PATCH /api/v1/me` (`name`, `city`).
- `GET/POST /api/v1/me/vehicles`, `PATCH/DELETE /api/v1/me/vehicles/{id}` — гараж
  покупателя, `vehicleId` из этого списка передаётся при создании запроса, чтобы не вбивать
  машину каждый раз (см. `title` в ответе — готовая строка для UI, например «Toyota Camry
  2018, 2.5 бензин»).

## Магазины

- `GET /api/v1/stores?category=&city=&page=&size=` — витрина для покупателя.
- `GET /api/v1/stores/{id}` — карточка магазина (рейтинг, филиалы, категории; `phone`
  филиала — см. правило про сделку выше).
- Кабинет продавца (`role=SELLER`, `/api/v1/my-store/**`):
  `GET/PATCH /api/v1/my-store` (название, описание), `GET/PUT /api/v1/my-store/categories`
  (от них зависит, какие запросы придут магазину), `GET/POST/PATCH/DELETE
  /api/v1/my-store/branches`, `GET/POST/PATCH/DELETE /api/v1/my-store/templates` (шаблоны
  для массового ответа).

## Запросы (покупатель) и лента (продавец)

- `POST /api/v1/requests` — создать и разослать.
- `GET /api/v1/requests/my`, `GET /api/v1/requests/{id}` (с офферами),
  `POST /api/v1/requests/{id}/extend` (+24ч), `POST /api/v1/requests/{id}/cancel`.
- `GET /api/v1/my-store/requests?filter=` — лента продавца, `POST
  /api/v1/my-store/requests/{id}/seen` — отметить просмотренным (для бейджа «новое»).
- `status` запроса: `ACTIVE → EXPIRED` (по сроку) или `ACTIVE → CANCELLED` (покупатель сам
  отменил). `COMPLETED` в модели данных есть, но сейчас ничем не проставляется — не
  полагайтесь на него как на признак «сделка состоялась», для этого смотрите на наличие
  чата (см. выше).

## Предложения (офферы)

- `POST /api/v1/offers` — точечный ответ на один запрос (роль `SELLER`).
- `POST /api/v1/offers/bulk` — массовый ответ шаблоном/текстом на несколько запросов сразу.
- Оба эндпоинта **сами создают/переиспользуют чат и шлют туда сообщение с офером** — см.
  «Основной флоу», пункт 4. Отдельного пуша «магазин ответил» больше нет — уведомление
  приходит как обычное `NEW_MESSAGE` от чата (с той же логикой «не слать, если покупатель
  и так смотрит этот чат прямо сейчас»).
- Статус оффера (`OfferResponse.status`) на практике сейчас всегда `ACTIVE` или `EXPIRED`
  (протухает вместе с запросом) — значения `ACCEPTED`/`REJECTED`/`CANCELLED` в enum
  остались от старого флоу и API их больше не проставляет, ориентироваться на них не нужно.
- `POST /api/v1/offers/{id}/accept|reject|cancel` **удалены**. Если где-то в старом клиенте
  или макетах ещё есть кнопки «принять/отклонить/отозвать предложение» — их нужно убрать,
  дальше сделка ведётся через чат (см. «Основной флоу»).

## Чат

REST — для истории и отправки, WebSocket — для live-доставки новых сообщений внутри уже
открытого чата.

- `POST /api/v1/stores/{storeId}/chat` — открыть/получить чат с магазином напрямую.
- `GET /api/v1/chats` — список своих чатов (и для покупателя, и для продавца — определяется
  токеном). Это стартовый снимок для экрана инбокса — дальше он живой: см. «Живой список
  чатов» ниже, обновлять вручную (pull-to-refresh) для этого больше не обязательно.
  Каждый элемент (`ChatResponse`, тот же формат и в `POST /stores/{id}/chat`) несёт снимок
  presence собеседника на момент запроса: `otherOnline: boolean`,
  `otherLastSeenAt: string?` (ISO-instant, `null` пока онлайн или ещё ни разу не
  отключался). Это стартовое состояние — дальше обновляется по WebSocket (см. «Presence»
  ниже).
- `GET /api/v1/chats/{id}/messages?page=&size=` — история, сначала новые.
- `POST /api/v1/chats/{id}/messages` `{ body }` — текстовое сообщение.
- `POST /api/v1/chats/{id}/messages/media` (`multipart/form-data`: `file`, `type` —
  `PHOTO|VOICE|VIDEO`, `caption?`, `durationSeconds?` для voice/video) — вложения. Отданные
  файлы раздаются статикой по `/media/**` (URL уже абсолютный в ответе, просто подставлять
  в `<img>`/плеер).
- `POST /api/v1/chats/{id}/read` — отметить прочитанным.

### WebSocket (live-доставка сообщений)

STOMP over WebSocket (нативный протокол Spring, не Socket.IO).

1. Подключение: `ws(s)://<host>/ws` (или `/ws` с SockJS-фоллбеком — эндпоинт
   зарегистрирован в обоих вариантах).
2. Браузер/клиент не может выставить обычный HTTP `Authorization` на WS handshake — токен
   передаётся **внутри STOMP CONNECT-фрейма**, нативным заголовком:
   ```
   CONNECT
   Authorization:Bearer <accessToken>

   ```
   (В библиотеках вроде `@stomp/stompjs` это `connectHeaders: { Authorization: 'Bearer ' + token }`.)
3. После CONNECT — подписка на конкретный чат: `SUBSCRIBE /topic/chats/{chatId}`. Сервер
   на SUBSCRIBE проверяет, что подключившийся пользователь — реально участник этого чата
   (покупатель или владелец магазина), иначе рвёт подписку.
4. Пуш приходит в момент, когда собеседник сохранил сообщение через
   `POST /chats/{id}/messages(/media)` — то есть сокет только доставляет уже сохранённые
   сообщения, вся валидация/бизнес-логика остаётся на HTTP. Тело пуша — тот же JSON, что
   возвращает `POST /chats/{id}/messages` (`MessageResponse`).
5. Топики: `/topic/chats/{id}` (сообщения), `/topic/chats/{id}/typing`,
   `/topic/chats/{id}/presence`, `/topic/chats/{id}/read` — все per-chat, подписываться на
   каждый открытый на экране чат отдельно. Плюс один топик на уровне пользователя —
   `/topic/users/{userId}/chats` — для экрана списка чатов, см. «Живой список чатов» ниже.

### Живой список чатов (инбокс)

Не нужно самому дёргать `GET /chats` по таймеру или pull-to-refresh — экран списка чатов
подписывается один раз и получает обновления по мере появления новых сообщений (в том числе
в чатах, которые сейчас не открыты).

- `SUBSCRIBE /topic/users/{myUserId}/chats` (сразу после CONNECT, `myUserId` — свой же,
  сервер проверяет, что это не чужой инбокс).
- Тело пуша — обычный `ChatResponse`, тот же формат, что в `GET /chats`/`POST /stores/{id}/chat`.
  Просто обнови/добавь эту строку в локальный список чатов по `id` (переставив её наверх, как
  в Instagram/WhatsApp).
- Триггерится: новое сообщение (текст/медиа) в любом из твоих чатов — `hasUnread:true`,
  свежий `lastMessage`; свой `POST /chats/{id}/read` — тот же чат прилетает с
  `hasUnread:false`; появление нового чата (кто-то впервые написал/открыл чат с тобой).

### «Печатает» (typing)

Чисто ephemeral WS-событие, без REST и без истории — ничего не сохраняется.

- Клиент **шлёт** (не получает) через STOMP SEND, а не HTTP:
  `SEND /app/chats/{chatId}/typing` с телом `{ "typing": true }` (и `{ "typing": false }`,
  когда перестал печатать). Сервер проверяет, что отправитель — участник этого чата, как и
  при подписке.
- Собеседник, подписанный на `SUBSCRIBE /topic/chats/{chatId}/typing`, получает
  `{ "userId": 5, "typing": true }`.
- Debounce/авто-сброс — забота клиента: сервер ничего не хранит и не таймаутит сам, шлите
  `typing:false` при отправке сообщения или после паузы в наборе (обычно 2–5 сек).

### «В сети» (presence)

- Начальное состояние приходит в REST — поля `otherOnline`/`otherLastSeenAt` в
  `ChatResponse` (см. «Чат» выше).
- Живые обновления — подписка `SUBSCRIBE /topic/chats/{chatId}/presence`:
  `{ "userId": 5, "online": true }` при подключении собеседника к сокету,
  `{ "userId": 5, "online": false }` при отключении последней его сессии (несколько
  вкладок/устройств одного пользователя не считаются офлайном, пока жива хотя бы одна).
  После оффлайн-события можно перезапросить `GET /api/v1/chats` (или ещё раз
  `POST /stores/{id}/chat`), чтобы получить свежий `otherLastSeenAt`.
- Онлайн — это факт открытого WebSocket-соединения, а не факт открытого экрана чата;
  «в сети» показывает, подключён ли собеседник к приложению вообще (сокет обычно держат
  открытым всё время работы приложения, не только на экране чата).

### «Прочитано» вживую (read receipts)

Раньше `readAt` было видно только перезапросив историю сообщений. Теперь отправитель узнаёт
о прочтении сразу:

- `SUBSCRIBE /topic/chats/{chatId}/read` — открывший чат-экран (или подписанный на этот чат)
  получает `{ "userId": 5, "readAt": "2026-09-22T10:00:00Z" }`, когда собеседник вызывает
  `POST /chats/{id}/read`.
- `userId` — кто прочитал; `readAt` — момент прочтения. У себя в UI помечай «прочитано»
  (галочки) все свои сообщения с `createdAt <= readAt` в этом чате.
- Статусов sent/delivered пока нет — только факт прочтения (как одна синяя галочка, а не
  три состояния WhatsApp). Если нужно различать «отправлено»/«доставлено» — это отдельная
  доработка бэкенда, сейчас не реализовано.

## Отзывы

- `GET /api/v1/stores/{storeId}/reviews?page=&size=`.
- `POST /api/v1/stores/{storeId}/reviews` `{ rating: 1..5, text?, offerId? }` — доступно,
  только если с этим магазином есть чат (см. «Основной флоу»); иначе 403.

## Аналитика продавца

- `GET /api/v1/my-store/analytics?period=WEEK|MONTH` → `requestsReceived`,
  `requestsAnswered`, `responseRate`, `requestsMissed`, `missedBudgetSum`,
  `avgResponseMinutes`, `dealsClosed` (= число открытых чатов с магазином за период),
  `topDemandedCategories`.

## Push-уведомления

- `POST /api/v1/devices` `{ token, platform: "IOS"|"ANDROID" }` — зарегистрировать
  push-токен после логина (и при каждом обновлении токена FCM/APNs).
- `DELETE /api/v1/devices/{token}` — снять при логауте.
- Пуши шлются на события: новый запрос продавцу (веерная рассылка) и новое сообщение в
  чате (`NEW_MESSAGE` — включая офферы, они тоже приходят как сообщение, см. «Основной
  флоу»; шлётся только если получатель прямо сейчас не смотрит этот чат). Отдельного
  пуша на оффер (`NEW_OFFER`) больше нет. В dev-режиме (`FCM_ENABLED=false`) пуши реально
  не уходят, только пишутся в outbox — рассчитывать на них в dev-стенде нельзя, тестировать
  через WebSocket/ручной опрос.

## Справочники (enum'ы)

- `PartCategory`: `BRAKES, SUSPENSION, ENGINE, WHEELS, LIGHTS, OILS, ACCESSORIES`.
- `UserRole`: `BUYER, SELLER`.
- `RequestStatus`: `ACTIVE, EXPIRED, CANCELLED` (`COMPLETED` в API сейчас не встречается,
  см. выше).
- `OfferStatus`: на практике `ACTIVE, EXPIRED` (остальные значения не используются, см.
  раздел «Предложения»).
- `SellerRequestFilter` (query-параметр ленты продавца): `ALL, URGENT, UNANSWERED`.
- `VerificationStatus` магазина: `NEW, VERIFIED, TRUSTED, BLOCKED`.
- `AnalyticsPeriod`: `WEEK, MONTH`.

## Известные ограничения (на сейчас)

- FCM-пуши выключены по умолчанию в dev — для мгновенной доставки в разработке
  ориентируйтесь на WebSocket, не на пуш.
- Явного отклонения/отзыва предложения больше нет — если магазин передумал, оффер просто
  висит `ACTIVE` до протухания запроса; отдельного действия «отозвать» для продавца сейчас
  не предусмотрено.
- У сообщений есть только факт прочтения (`readAt` / read-receipt по WS), нет отдельных
  статусов «отправлено»/«доставлено».
- Фото и видео сохраняются как есть, без серверных миниатюр/превью и без сжатия — если нужен
  маленький превью для списка чатов, генерировать на клиенте.
